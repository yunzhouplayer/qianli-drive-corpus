# 飞书权限控制台集成设计

## 1. 文档状态

- 设计日期：2026-08-27
- 当前阶段：架构设计已通过口头评审，等待书面审阅
- 适用范围：知识库管理后台 MVP 与后续生产化设计
- 当前运行模式：`governance_validation`
- 生产索引：保持关闭

本设计是《飞书 + LLM Wiki 企业知识库架构审批方案》的权限治理补充。它不改变以下既有结论：飞书知识库仍是正文、版本、目录位置和实际 ACL 的权威来源，管理后台、Git、缓存、生成 Wiki 和 MCP 均不得维护一套可以脱离飞书独立生效的访问权限。

批准本设计只表示批准架构方向，不代表授权立即申请飞书写权限、修改生产文档权限、开启生产 MCP 或使用真实敏感文档验证。

## 2. 背景与问题

管理后台已经承担文档准入、自动检查、元数据、审批、编译和索引状态管理。如果文档增删改查在控制台完成，而权限变更仍完全依赖管理员进入飞书知识库操作，会产生以下问题：

1. 操作者需要在两个系统之间切换，治理流程被割裂；
2. 审批决定、实际权限变更和 AI 派生数据失效难以形成统一审计链；
3. 权限收紧后，MCP、raw 缓存、生成 Wiki 和索引可能不能及时失效；
4. 如果后台复制并独立维护成员名单，又会形成双写和权限泄漏风险。

因此，控制台应成为权限变更的统一申请、审批编排、执行和审计入口，但所有真实权限仍由飞书保存和执行。

## 3. 目标与非目标

### 3.1 目标

1. 在控制台中查看飞书当前实际权限和继承来源；
2. 在控制台中发起文档、目录和知识空间权限变更；
3. 使用当前登录人的飞书 OAuth 身份执行变更；
4. 按风险等级选择自动执行或管理员二次确认；
5. 执行后回读飞书 ACL，确认一致后才完成流程；
6. 权限变化与 MCP、缓存、生成 Wiki、索引和审计联动；
7. 无法确认权限时默认拒绝访问，不泄漏隐藏资源存在性。

### 3.2 非目标

1. 不在管理后台创建第二套独立 ACL；
2. 不用高权限应用身份替代所有空间管理员；
3. 不绕过飞书租户安全策略、密级策略和管理员限制；
4. 不在 Git 中保存用户、群组、部门或应用的完整权限成员表；
5. MVP 不开放任意批量授权、所有者转移、外部公开分享或密级豁免的自动执行；
6. 本阶段不执行真实飞书权限写入。

## 4. 核心决策

### 4.1 权威边界

|对象|权威来源|控制台职责|
|---|---|---|
|文档、目录和知识空间 ACL|飞书|实时读取、展示、申请、编排、执行和回读验证|
|权限变更申请|管理后台数据库|保存申请、差异、状态和操作证据|
|人工审批决定|飞书审批|控制台发起并同步状态，不伪造审批结果|
|规则、风险分类和受控策略|治理 Git|版本化、评审和校验|
|MCP、缓存、生成 Wiki 和索引状态|运行存储|根据飞书 ACL 变化失效、重建和审计|

控制台保存的 ACL 快照只用于展示、差异计算和短期预检，不能作为最终授权依据。任何授权判断和执行结果均以飞书回读结果为准。

### 4.2 执行身份

默认使用当前登录人的飞书 OAuth 用户身份执行权限变更：

- 操作者必须在飞书中拥有目标资源的实际管理权限；
- 控制台不得通过应用管理员身份扩大操作者原有权限；
- 用户访问令牌和刷新令牌只保存在服务端加密凭证存储；
- 本地 Agent 不接触飞书用户令牌；
- 应用身份只用于已授权资源的读取、审批编排、回调接收和受控后台任务；
- 用户身份失效或权限不足时，流程停止并要求重新认证或更换有权执行人。

### 4.3 分级执行

|风险等级|典型操作|执行方式|
|---|---|---|
|低|内部员工新增只读权限、设置明确失效时间|审批通过后自动执行并回读验证|
|中|编辑权限、单人撤销、内部群组授权、继承范围调整|审批通过后自动执行；规则命中时升级为二次确认|
|高|外部分享、部门批量授权、空间管理员、所有者转移、公开链接、密级变更|审批通过后进入“待执行”，授权管理员二次确认并重新验证身份|
|禁止自动执行|绕过租户安全策略、移除最后管理员、影响范围不明、权限继承冲突|停止执行并提供飞书原生处理入口|

## 5. 权限能力分层

### 5.1 文档和文件协作者

通过飞书 Drive 权限成员接口管理单个文档、文件、文件夹或 Wiki 底层对象的协作者。支持的对象类型和权限档位必须在实现时从飞书实际接口 Schema 获取，不在代码中猜测。

官方能力参考：

- [增加协作者权限](https://open.feishu.cn/document/server-docs/docs/permission/permission-member/create)
- [修改协作者权限](https://open.feishu.cn/document/server-docs/docs/permission/permission-member/update)
- [删除协作者权限](https://open.feishu.cn/document/server-docs/docs/permission/permission-member/delete)

### 5.2 知识空间成员

空间管理员和空间成员属于 Wiki 空间层权限。空间成员变更必须使用真实 `space_id`，并区分用户、群组、部门和应用等成员类型。角色切换如果飞书接口不支持原子更新，应按“读取旧角色 → 删除旧角色 → 添加新角色 → 回读验证”的受控步骤执行。

### 5.3 权限继承

控制台必须明确区分：

- 直接授权；
- 父目录继承；
- 知识空间成员继承；
- 租户级策略；
- 文档密级或安全策略限制。

继承权限不能在文档层伪造覆盖。操作者修改继承权限时，控制台应跳转到实际授权来源，并在执行前展示受影响的全部已知文档、目录、权限域和 AI 派生数据。

### 5.4 公开范围和高风险安全设置

公开链接、外部访问、所有者转移、空间管理员和密级调整属于高风险能力。MVP 只展示当前状态、发起申请和记录审批；真实执行默认要求管理员二次确认，飞书租户或密级策略拒绝时不得绕过。

## 6. 控制台交互设计

“知识目录控制台”右侧详情区增加以下页签：

1. **治理概览**：来源版本、准入、缓存、编译、MCP 和有效状态；
2. **飞书权限**：实时 ACL、成员、权限档位、授权类型、继承来源、有效期和校验时间；
3. **变更记录**：权限申请、审批、执行、回读和派生数据处理状态；
4. **审计轨迹**：操作者、身份、目标、差异、审批单号、接口结果摘要和时间。

主要操作为“发起权限变更”。表单至少包含：

- 目标资源；
- 目标对象类型和稳定标识；
- 新增、调整或撤销；
- 权限档位；
- 生效时间和失效时间；
- 变更理由；
- 审批路线；
- 继承来源；
- 影响范围。

提交前必须展示“变更前 / 变更后”差异，以及对 MCP、raw、生成 Wiki、索引和当前访问者的影响。

## 7. 标准流程

```text
选择资源
  → 使用当前用户身份读取飞书 ACL
  → 创建权限变更草稿
  → 解析继承来源和影响范围
  → 确定性规则预检
  → 冻结申请快照
  → 发起飞书审批
  → 审批结果同步
  → 普通操作自动执行 / 高风险操作二次确认
  → 调用飞书权限接口
  → 回读飞书 ACL
  → 验证预期差异
  → 更新派生数据状态
  → 完成审计
```

审批期间如果目标 ACL、资源版本、目录位置、操作者身份或治理规则发生变化，原申请进入 `stale`，必须重新预检和审批，不能直接执行旧快照。

## 8. 状态模型

```text
draft
  → prechecking
  → ready_for_approval
  → approving
  → approved / rejected / stale
  → awaiting_execution / executing
  → verifying
  → propagating
  → completed
```

异常状态：

- `reauth_required`：用户身份或令牌失效；
- `blocked_by_feishu_policy`：被租户安全、公开分享或密级策略阻止；
- `permission_denied`：操作者没有目标资源管理权；
- `partial_failure`：批量子任务部分成功；
- `verification_failed`：飞书回读结果与预期不一致；
- `propagation_failed`：飞书变更成功，但派生数据失效或重建失败；
- `cancelled`：申请人在执行前取消。

只有飞书回读验证和派生状态处理全部完成后，状态才能进入 `completed`。

## 9. 数据对象

|对象|职责|关键字段|
|---|---|---|
|`PermissionChangeRequest`|权限变更主单|申请人、资源引用、动作、理由、风险等级、状态、规则版本|
|`PermissionTarget`|变更对象|成员类型、稳定 ID、目标权限、有效期|
|`AclSnapshot`|短期权限快照|飞书资源引用、读取身份、成员摘要哈希、继承来源、获取时间|
|`PermissionDiff`|预期差异|增加、调整、撤销、影响范围|
|`ApprovalBinding`|飞书审批关联|审批定义、实例编号、审批状态、最终决定时间|
|`ExecutionAttempt`|执行证据|执行人、OAuth 身份、接口动作、结果码、回读结果、重试次数|
|`DerivativeImpact`|派生数据影响|MCP、raw、Wiki generation、索引的失效与重建状态|
|`AuditEvent`|不可变审计事件|主体、动作、目标、决定、时间、关联请求和结果摘要|

ACL 快照不保存正文、访问令牌或不必要的个人信息。Git 中只保存 Schema、受控规则和匿名化测试夹具。

## 10. 批量操作与一致性

飞书权限接口不应被假定具有跨资源事务能力。批量申请必须拆分为独立子任务：

1. 主申请负责审批和总体影响说明；
2. 每个资源和成员组合生成独立执行子任务；
3. 每个子任务单独执行、回读和审计；
4. 任一子任务失败时停止后续高风险操作；
5. 已成功的子任务不得被界面显示为“整体失败且无变更”；
6. 只有在反向操作经过预检且不会扩大权限时，才允许自动补偿。

MVP 默认限制为单资源、少量成员。任意跨空间批量授权不纳入 MVP。

## 11. 与 AI 派生数据联动

### 11.1 权限收紧

1. 变更进入执行阶段前，相关 MCP 来源立即进入拒绝或暂停状态；
2. 飞书权限变更成功后，raw 缓存、生成 Wiki 和索引进入失效状态；
3. 回读 ACL 并重新确定权限域；
4. 清理或重建派生数据；
5. 完成权限泄漏负例验证后恢复服务。

飞书写入失败时，MCP 继续保持拒绝状态，直至管理员确认实际 ACL 和派生数据一致。

### 11.2 权限扩大

1. 先执行并回读飞书权限；
2. 再计算新的 ACL 权限域；
3. 重建 raw、生成 Wiki 和索引；
4. 完成有权、无权和撤销对照验证；
5. 最后开放 MCP 访问。

不得因为审批已经通过而提前向用户返回尚未在飞书生效的内容。

## 12. 安全控制

1. OAuth 使用最小必要 scope，并区分只读和权限写入能力；
2. 用户令牌使用专用加密存储，日志、Git、前端和 Agent 不得出现明文；
3. 所有权限写入必须绑定已认证用户、目标资源和已批准申请；
4. 执行接口必须防重放、支持幂等键并限制目标范围；
5. 操作者不得修改自己的执行证据和审批结果；
6. 外部分享、所有者转移和管理员变更必须二次确认；
7. 飞书不可用、身份过期、ACL 不明或回读失败时默认拒绝；
8. 无权用户不得通过权限查询接口获知隐藏文档、成员或目录结构。

## 13. 错误与恢复

|场景|处理|
|---|---|
|OAuth 过期|进入 `reauth_required`，重新认证后重新预检|
|审批期间 ACL 变化|进入 `stale`，重新生成差异并重新审批|
|飞书权限不足|进入 `permission_denied`，由有权管理员接管或终止|
|租户或密级策略拦截|进入 `blocked_by_feishu_policy`，提供飞书原生入口|
|接口超时|使用幂等键有限重试，之后必须回读确定实际结果|
|回读不一致|进入 `verification_failed`，禁止显示成功|
|派生数据处理失败|进入 `propagation_failed`，MCP 保持拒绝|
|批量部分成功|记录每个子任务结果，禁止掩盖部分成功|

## 14. MVP 范围

### 14.1 纳入 MVP

- 单个无敏感测试文档的权限只读展示；
- 直接授权和继承授权标识；
- 权限变更草稿、差异和影响预览；
- 飞书审批状态模拟或沙箱同步；
- 普通操作与高风险操作分流；
- 写入执行器的接口契约和模拟实现；
- 回读校验、审计和派生数据失效模拟；
- 有权、无权、撤销和过期身份测试。

### 14.2 不纳入 MVP

- 生产权限写入；
- 真实外部分享和公开链接修改；
- 所有者转移、密级豁免和移除最后管理员；
- 跨空间批量授权；
- 后台独立 ACL 决策；
- 生产 MCP 和生产索引。

## 15. 验收门禁

1. 控制台展示的当前权限来自飞书实时读取，并标明获取时间和身份；
2. 直接授权和继承授权可以被明确区分；
3. 无权用户无法获知隐藏资源或成员信息；
4. 普通和高风险操作按规则正确分流；
5. 旧 ACL、版本或目录变化会使申请进入 `stale`；
6. 飞书写入后必须回读验证，回读失败不得完成；
7. 权限收紧时 MCP 在飞书执行前进入拒绝状态；
8. 权限扩大时 MCP 只在飞书确认和派生数据重建后开放；
9. 批量部分成功能够逐项审计；
10. 日志、Git、浏览器和测试产物中不出现令牌和完整 ACL 成员表；
11. 权限泄漏负例出现一次失败，MVP 即不得进入生产阶段。

## 16. 后续实施顺序

1. 更新 HTML 原型，加入权限页、变更抽屉、影响预览、审批和执行状态；
2. 定义权限请求、ACL 快照、执行证据和派生影响 Schema；
3. 实现只读权限适配器和模拟写入执行器；
4. 使用无敏感测试节点验证读取、继承识别和风险分流；
5. 单独审批飞书权限写入 scope 和测试对象；
6. 在隔离测试空间执行最小权限写入、回读和撤销烟测；
7. 完成权限泄漏和撤销传播验证后，再评估生产化。
