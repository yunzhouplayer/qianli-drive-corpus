# 知识库治理体系方案 B 精简迁移设计

## 1. 结论

采用方案 B：在不改变治理能力、安全边界和权威来源的前提下，合并重复的人用文档、收敛机器控制字段、抽取飞书工具公共能力，并规范目录与文件命名。

本次是中度精简，不追求最少文件数。目标是将日常维护复杂度降低约 25%～35%，同时保留以下不可削弱的控制：

- 默认拒绝未登记正文发布；
- 写入飞书前必须先生成只读差异和预检结果；
- 所有真实写入必须显式使用 `--execute`；
- 发布与退役继续使用两个独立命令；
- 飞书写入后必须回读验证；
- 身份范围、空间授权和文档 ACL 分别校验；
- 准入、ACL、权威来源、语料范围、评测与保留期限继续分离；
- 飞书正文和权限不被 Git 自动反向覆盖；
- 空语料、空权威来源或空评测集不得被描述为“生产可用”或“质量通过”。

实施继续保持：

- `operating_mode=governance_validation`；
- `production_index_enabled=false`；
- 不补写或评判具体业务正文；
- 不建设生产索引、向量库或本地 AI 服务；
- 不批量重命名、移动或删除 Validation&Verification 的 301 个现有飞书节点。

## 2. 当前问题

### 2.1 面向人员的内容重复

当前飞书发布清单包含 17 篇正文，存在四层入口和多处重复说明：

- 治理根 README、人员 README、主指南和空间蓝图都承担部分导航职责；
- 飞书与 Git 的权威边界在多篇文档重复；
- 使用、管理、命名、元数据和生命周期规则被拆成多篇短文；
- 主指南文件名包含 `V2`，与“版本写入元数据、不写入文件名”的规则不一致。

此外，当前飞书发布工具会把 Markdown 本地链接按普通文本写入飞书，人员 README 在飞书内不能真正承担导航入口。

### 2.2 面向 AI 的控制重复

- 全局运行模式在启动清单、准入规则、检索契约和索引策略中重复声明；
- 检索契约重复列举请求、响应和错误码字段，与独立 Schema 已发生轻微漂移；
- 准入规则重复定义决定载荷字段；
- 索引策略混合了长期安全原则与可调运行参数；
- 权威来源登记结构包含应从飞书实时读取的标题、负责人和更新时间等动态事实；
- 结构蓝图中路径、名称、状态、继承策略和通用属性大量重复。

### 2.3 工具和命名问题

- 飞书发布与退役脚本重复实现鉴权、配置、API 客户端、分页、限流、状态和范围校验；
- `import` 已不准确，实际行为是受控正文发布，应统一使用 `publish`；
- 退役工具仍固化一次性的 59 节点清理常量；
- 飞书发布配置和脚本放在“面向 AI”目录，职责不匹配；
- Validation&Verification 使用英文名称和下划线序号，但尚未建立中文显示名和稳定绑定；
- 验证记录的三个 YAML 附件使用超长并列文件名；
- 部分英文 Schema 容器字段缺少中文 `description`；
- `docs/` 是工程设计目录，但尚未声明其编号和发布例外。

## 3. 权威来源与同步边界

精简后继续使用单向受控协作，不建立“最后写入者胜出”的双向同步。

| 信息类型 | 权威来源 | Git 中的作用 | 飞书中的作用 |
| --- | --- | --- | --- |
| 公司知识正文 | 飞书 | 不保存生产正文副本 | 正文编辑、版本记录、协作 |
| 文档元数据值 | 飞书 | 保存字段 Schema 与字典 | 保存每篇文档的实际值 |
| 权限与成员关系 | 飞书 | 保存策略和校验规则 | 执行真实 ACL |
| 目录稳定 ID 与目标结构 | Git | 保存蓝图和绑定配置 | 承载实际空间与节点 |
| 准入、索引、检索和评测规则 | Git | 唯一权威控制面 | 发布必要的人读说明 |
| 发布清单与路径迁移 | Git | 显式白名单和稳定映射 | 接收受控发布结果 |
| 索引、缓存、审计和运行状态 | `.runtime/` | 不提交，可重建 | 不作为运行态存储 |

同步方向固定为：

1. Git 控制面经过本地校验；
2. 对 12 篇治理说明，Git Markdown 只作为变更提案和可审计发布种子，不因存在于 Git 而自动取得飞书正文权威；
3. 发布工具先读取飞书当前正文，以“上次已同步版本、当前飞书版本、当前 Git 提案”做三方比较；
4. 飞书自上次同步后有人工作修改时自动停止，必须先保留该修改并完成人工合并；
5. 只有远端未漂移或管理员已逐页批准合并结果时，工具才生成 Git → 飞书正文差异；
6. 管理员显式执行后，飞书接收治理正文；
7. 工具回读正文块、节点标记和路径并验证；
8. 后续正文采集器只能从飞书读取公司知识正文，不能用 Git 副本覆盖飞书；
9. 飞书 ACL 在查询和读取前实时或按有效期缓存校验，Git 不复制成员权限表。

## 5. 机器控制面精简

### 5.1 启动清单

启动清单仍是唯一机器入口，但删除可从 Schema 或列表位置推导的重复字段：

- 保留控制面版本、全局运行状态、按顺序排列的必需文件和 Schema 引用；
- 保留显式控制项类型或格式；`.yaml` 同时用于普通控制实例和 JSON Schema，不能仅凭扩展名推导；
- 保留冲突优先级、fail-closed 规则和运行态边界；
- 删除每项重复的 `required=true` 和与数组顺序完全相同的重复序号；
- 不允许扫描任意目录自动发现控制文件。

### 5.2 结构蓝图 v2

结构蓝图升级为 v2，但保留所有空间和目录稳定 ID。使用默认值与局部覆盖替代逐项重复：

- 路径由父节点和当前名称递归生成，不再同时维护 `name` 与完整 `path`；
- `status=active`、权限继承和通用索引属性放入默认配置；
- 只有差异项显式覆盖；
- 目录权限名称中的“按目录授权”“严格授权”等展示后缀移除，真实控制仍由 `access_policy` 表达；
- 校验器先展开为规范化树，再执行 ID、路径、序号、管理员、权限和引用检查；
- v1 → v2 迁移脚本必须对展开结果做逐节点等价比较，预期仍为 9 个空间、134 个目录；任何 ID、生成路径或控制属性变化都阻断提交。

Validation&Verification 先作为外部现有节点绑定登记：

- 稳定 ID 和中文显示名建议为“验证与确认（Validation&Verification）”；
- 保留飞书当前物理名称和八个一级分支，不在本次批量改名；
- 不把 301 个业务节点纳入治理正文发布清单；
- ACL 继续从飞书读取，不在 Git 中推测；
- 下划线序号改名另行生成影响评估和迁移计划，未经确认不执行。

301 个节点是 2026-08-14 的只读基线。阶段 4 开始前重新采集节点 ID 清单；若期间发生正常业务新增或调整，先记录漂移并由管理员重新确认基线，不通过强行恢复数量覆盖业务变化。

### 5.3 Schema 中文说明

所有英文机器控制文件保留中文文件头。Schema 中业务属性和对象容器必须有中文 `description`，至少补齐当前已发现的 23 个容器字段。条件分支中重复出现、且已由主定义说明的判定字段不要求复制相同描述。

Schema 执行统一基于 JSON Schema Draft 2020-12。现有命令保留为兼容入口，但内部调用同一校验实现，避免三个不完整的手写解释器继续分叉。

## 6. 飞书工具重构

### 6.1 公共库边界

`feishu-governance-core.mjs` 只抽取发布与退役确实共用的能力：

- 安全哈希和日志脱敏；
- Keychain 和环境配置读取；
- tenant/user token 获取；
- Feishu API 客户端、限流、分页和错误归一化；
- wiki 节点、文档块和运行状态读取；
- 应用/用户身份范围诊断；
- 管理标记解析和回读校验。

发布决策、正文转换和退役决策不得放入公共库，避免两个命令重新耦合。

### 6.2 命令兼容

- 正式命令改名为 `feishu-governance-publish.mjs`；
- 原 `feishu-governance-import.mjs` 暂保留一个版本，作为只转发参数的兼容入口并输出弃用提示；
- `.runtime/feishu-import-state.json` 迁移为 `.runtime/feishu-publication-state.json`，首次运行可读取旧状态并原子写入新状态；
- Keychain 服务名迁移到 governance 命名，先读新名称，缺失时兼容读取旧 `qianli-feishu-smoke`，任何路径都不得打印密钥；
- 统一入口 `validate_governance.rb` 编排结构、控制面、元数据和评测校验；原校验命令继续作为兼容包装。

控制文件重命名与所有路径消费者必须在同一原子阶段完成：启动清单、README、Schema 引用、Ruby/Node 脚本、测试、两个 Skill 及其 `references/` 都要使用新路径。`03-index-admission-rules.yaml` 移除状态值时，`prepare-knowledge-document`、`review-knowledge-admission` 和 Skill 内的元数据校验器必须改为沿 `state_ref` 读取唯一启动清单；迁移完成前不得删除原字段。

### 6.3 飞书内导航

发布正文前，工具先完成全部目标节点解析，再转换 Markdown 链接：

- 相对 `.md` 链接解析为仓库规范路径；
- 目标位于发布清单且已绑定节点时，写为真实飞书节点链接；
- 外部 `https` 链接保持原地址；
- 指向 Git-only 文件的链接改为文字说明或明确的 Git 地址，不伪装成飞书内链；
- 无法解析的本地链接使预检失败，不再静默写成普通文本；
- 锚点无法稳定映射时链接到目标页面，并在链接文字中保留章节名；
- 回读校验同时检查链接目标，而不只检查可见文字。

## 7. 飞书正文迁移策略

飞书迁移不删除旧页面。顺序如下：

1. 在 Git 中完成文件合并、路径映射和 12 篇发布清单；
2. 运行全部离线校验和飞书发布 mock 回归；
3. 使用真实只读 API 拉取 17 篇现有正文，检查是否包含上次同步后产生的人工修改；
4. 有人工修改时先生成逐页三方合并结果并停止，未确认前不得写入；
5. 无冲突或合并结果已获确认后，生成 17 → 12 的节点与正文差异；
6. 确认 12 个目标节点都能创建、复用或重命名，且旧节点均有稳定去向；
7. 管理员显式执行正文发布；
8. 对 12 个有效页面逐页回读正文、链接、路径和管理标记；
9. 对不再有效的 5 个旧页面写入“已合并至……”说明和飞书链接，保留版本历史；

## 9. 验收标准

- 全局运行模式只存在一个权威声明；

- Validation&Verification 以执行前确认的节点基线为准，正文和 ACL 均未被本次迁移改动；若基线仍为 2026-08-14 快照，则数量为 301。

- 空权威来源、空语料和空评测集仍返回“未执行/未就绪”，不得返回质量通过。

## 10. 回滚设计

- Git：每阶段独立提交，可按阶段反向恢复；不使用破坏性重置覆盖用户改动；
- 文件路径：所有重命名写入路径迁移表，发布状态优先按管理标记和稳定 ID 匹配，不按标题猜测；
- 运行状态：新发布状态写入成功前保留旧 import 状态文件，只做原子迁移；
- Keychain：新服务读取失败时回退旧服务，迁移完成前不删除旧条目；
- 飞书正文：逐页写入、逐页回读，依赖飞书版本历史恢复；失败时停止后续页面；
- 飞书节点：本次不删除旧页面、不删除治理镜像、不移动或重命名 V&V 业务节点；
- 权限：本次不修改飞书 ACL，任何权限差异都视为阻断项。

## 11. 明确不做

- 不检查具体业务知识是否完整、正确或最新；
- 不把 V&V 的 301 个业务节点复制到 Git；
- 不实现生产飞书采集器、RAG、MCP、Embedding 或重排服务；
- 不把飞书正文变成 Git 权威副本；
- 不把 Git 权限策略当作真实飞书成员授权；
- 不因精简而合并准入与 ACL、权威来源与语料、评测与运行日志；
- 不自动退役仍可访问的飞书页面或空目录镜像；
- 不使用未经实测的索引参数作为生产默认值。
