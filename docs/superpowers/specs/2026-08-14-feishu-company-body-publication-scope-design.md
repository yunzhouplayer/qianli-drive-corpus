# 飞书公司知识正文发布范围整改设计

## 1. 背景与结论

当前飞书导入器按扩展名扫描整个 Git 仓库，会将 Markdown、YAML、JSON、Ruby、JavaScript 和 `.gitignore` 等文件统一映射为飞书页面。现有本地计划包含 61 个文件和 147 个目录节点，其中混入接入验证报告、元数据旁车文件、Schema、受控字典、脚本和 Skill 源码。

本次整改将导入模型改为“默认拒绝、显式发布”：飞书只承载公司知识正文、必要导航、填写模板和业务分类目录；Git 继续承载机器控制、自动化实现、测试证据和审查过程记录。

本次只整改本地发布规则、测试和说明文档，不删除、移动或覆盖飞书现有测试节点，不开启生产索引。

## 2. 目标与非目标

### 2.1 目标

1. 当前默认发布范围只包含 14 个已确认的人员侧规范、导航和模板。
2. 保留 01 至 08 业务知识空间的目录蓝图，便于后续文件管理；空目录不等于已有业务知识。
3. 新增文件默认不发布，必须经过明确登记后才能进入飞书计划。
4. 机器控制文件、测试过程文件、代码和 Skill 源码不生成飞书正文页面。
5. 计划输出能够说明纳入、排除和目录数量，并继续执行敏感信息门禁。
6. 旧导入状态中存在超出新范围的节点时，写入流程必须阻塞并报告数量，不能静默声称整改完成。

### 2.2 非目标

- 不删除或移动当前飞书 `qianli-drive-Corpus` 测试子树。
- 不把 3 个管理员侧 AI/索引治理文档默认发布到普通员工正文区。
- 不启用生产索引、Agent 公司事实回答或模型训练。
- 不迁移真实业务文档，也不代替业务负责人补充权威来源或元数据。
- 不在本次整改中实现飞书自定义元数据字段；正式启用前必须单独验证其结构化存储和 API 读取能力，未验证时继续阻塞生产准入，不能改以 Git 猜测正文元数据。

## 3. 方案比较

### 方案 A：继续按扩展名放行

实现成本最低，但任何新建的 Markdown、YAML 或脚本都会自动进入飞书，无法满足“只发布正文”的目标，不采用。

### 方案 B：维护排除目录和文件列表

可快速排除现有测试与技术目录，但新出现的过程文件容易漏网，规则会持续膨胀，不采用。

### 方案 C：显式发布清单，默认拒绝

新增机器可读的发布清单，逐项登记允许发布的文件，并单独登记允许创建的业务目录根。未登记文件不进入计划。这一方案审计边界清楚，能够支持后续准入流程，采用本方案。

## 4. 飞书与 Git 的权威边界

本项目不设置一个覆盖所有对象的“全局唯一主库”，而是按数据类别确定唯一权威来源，避免飞书和 Git 双向可写后发生冲突。

|数据类别|唯一权威来源|另一侧的角色|
|---|---|---|
|公司业务正文、人员侧治理正文|飞书知识库|Git 只保存首次创建种子或脱敏备份，不作为在线正文|
|文档标题、正文版本、负责人、状态及文档级元数据值|飞书知识库|Git 可保存校验结果或引用，不反向覆盖|
|空间、目录、成员和文档实际访问权限|飞书实时 ACL|Git 只定义原则、期望结构和最小权限策略|
|Schema、受控字典定义、准入规则、目录稳定 ID 和 AI 使用契约|Git|飞书可提供人员可读说明，不作为机器规则源|
|发布清单、自动化脚本、Skill 源码和测试|Git|不发布为飞书公司正文|
|主题到权威文档的机器映射|Git 中的权威来源注册表|每条记录必须引用真实飞书文档 ID、链接和业务审批依据|
|索引、缓存、自动摘要和语料清单|运行系统，可从源重建|永不成为公司事实权威来源|

发生冲突时按以下规则处理：

1. 正文内容、标题、页面版本和文档元数据值以飞书当前正式页面为准。
2. Schema、受控字典、准入条件和 AI 处理策略以 Git 当前已批准版本为准。
3. 飞书 ACL 是访问判断的最终否决条件；Git 即使允许索引，只要飞书不可访问就必须拒绝。
4. AI 使用一份文档必须同时满足飞书来源正式有效且可访问、Git 治理规则允许；任一侧拒绝即拒绝。
5. 索引或 Git 快照与飞书正文不一致时，停止引用并重新同步，不能用副本覆盖飞书权威正文。

### 4.1 协同数据流

1. Git 中维护目录蓝图、Schema、字典和准入规则。
2. 发布清单只用于从 Git 首次创建已批准的正文种子和必要目录。
3. 创建成功后回填飞书文档 ID、源链接、创建时间和更新时间；该飞书页面成为正文权威源。
4. 后续正文编辑、权限设置、审批、版本历史和归档在飞书完成。
5. 校验或索引流程从飞书读取正文、元数据和 ACL，再按 Git 规则判断是否可用。
6. Git 只记录稳定引用、机器规则和校验结果，不持续反向覆盖飞书正文。

### 4.2 导入器写入边界

导入器从持续镜像工具收紧为“首次创建与结构引导工具”：

- 页面不存在时，允许按发布清单创建并写入初始正文。
- 页面创建成功后，在本地状态中标记 `content_authority=feishu`。
- 已标记为飞书权威的页面，后续 `apply` 不因 Git 文件哈希变化覆盖正文。
- `verify` 核验节点身份、父子关系、权威标记和可访问性，不要求飞书正文块数与 Git 种子完全一致。
- 如果需要用 Git 新版本替换飞书正文，必须另行发起内容变更并由文档负责人审批，不属于自动导入流程。

目录蓝图由 Git 定义期望分类和稳定 ID，但飞书中的实际节点、权限及其变更记录以飞书为准。结构漂移应报告并走治理变更，不自动移动或删除节点。

## 5. 发布清单设计

新增 `00-知识库治理与索引/01-面向AI/10-feishu-publication-manifest.json`，使用 JSON 是为了让 Node.js 导入器无需增加第三方 YAML 依赖。文件必须包含中文说明字段。

清单包含：

- `schema_version`：当前固定为 `1.0`。
- `description_cn`：中文说明发布目的和维护边界。
- `default_action`：固定为 `deny`。
- `files`：允许发布的项目相对文件路径精确列表。
- `directory_roots`：允许建立目录页面的目录根列表。

文件发布不支持通配符。这样可以保证新增业务文档必须经过准入并显式登记，不能因为扩展名相同而自动进入飞书。

默认 `files` 登记以下 14 个文件：

1. `00-知识库治理与索引/README.md`
2. `00-知识库治理与索引/00-面向人员/README.md`
3. `00-知识库治理与索引/00-面向人员/01-千里智行·公司知识库结构设计与管理指南-V2.md`
4. `00-知识库治理与索引/00-面向人员/02-公司知识库空间与目录蓝图.md`
5. `00-知识库治理与索引/00-面向人员/03-知识库使用手册.md`
6. `00-知识库治理与索引/00-面向人员/04-知识库管理规范.md`
7. `00-知识库治理与索引/00-面向人员/05-文档命名规范.md`
8. `00-知识库治理与索引/00-面向人员/06-元数据填写规范.md`
9. `00-知识库治理与索引/00-面向人员/07-权限与安全规范.md`
10. `00-知识库治理与索引/00-面向人员/08-生命周期与质量规范.md`

默认 `directory_roots` 包含人员侧治理目录和 01 至 08 业务知识空间。技术目录 `docs`、`01-面向AI`、`02-Skills`、`scripts`、`schemas`、`vocabularies`、`10-验证记录` 不作为目录根；仅当某个已发布文件需要父目录时，导入器自动补齐其祖先目录。

当前单父节点导入器只能把 01 至 08 空间表现为烟测子树中的目录，用于验证分类结构，不代表正式飞书空间已经建立。生产阶段必须分别绑定真实飞书空间及其管理员和 ACL，不得把测试根下的目录页冒充独立知识空间。

## 6. 扫描与数据流

1. 导入器读取并校验发布清单。
2. 扫描项目文件系统，但只收集清单登记的文件。
3. 收集 `directory_roots` 下的真实目录；继续忽略 `.gitkeep` 文件。
4. 自动补齐所有已发布文件和目录的祖先目录，保证父子关系完整。
5. 对纳入的文件执行文本格式检查和敏感信息门禁。
6. 对清单中不存在、重复、越界、为符号链接或不是普通文件的路径直接报错。
7. `plan` 输出发布文件数、目录数、块数、字节数，以及默认拒绝策略和发布清单路径。
8. 只有通过计划和远端状态一致性检查后，后续 `apply` 才能首次创建缺失页面；已经移交给飞书的正文不自动更新。

## 7. 旧测试树与状态处理

当前本地状态记录了旧的全仓库镜像节点。新范围生效后，这些记录会成为“超出发布范围的受控节点”。

- `plan` 仍可纯本地运行，用于验证新目标范围。
- `preflight`、`apply` 和 `verify` 读取到超范围状态节点时必须阻塞，并报告 `retired_managed_nodes` 数量。
- 导入器不得自动删除、移动、隐藏或接管这些节点。
- 后续需单独制定飞书测试树清理方案，经用户明确确认后执行；清理完成并建立干净状态后，才能进行新范围的真实写入与核验。

该处理避免把“本地规则已整改”误报为“飞书页面已清理”。

## 8. 测试与验收

### 8.1 自动化测试

扩展现有本地回归，至少覆盖：

1. 只有清单中的文件进入计划。
2. 未登记的 Markdown、YAML、脚本和 `.gitignore` 不进入计划。
3. 业务目录根和必要祖先目录被保留。
4. 缺失、重复、越界和非法类型的清单路径被拒绝。
5. 纳入文件中的密钥或令牌仍会触发敏感信息门禁。
6. 旧状态存在超范围节点时，写入和核验被阻塞。
7. 使用干净状态时，首次导入、幂等重跑和读回核验继续通过。
8. 首次创建后修改 Git 种子不会覆盖已标记为飞书权威的正文。
9. 飞书正文发生正常编辑后，核验不会把“与 Git 哈希不同”误判为应自动覆盖。

### 8.2 本地验收标准

- 导入器单元/集成回归全部通过。
- 知识结构校验全部通过。
- 当前项目 `plan` 显示 `files=14`。
- `plan` 中不出现 `10-验证记录`、`docs/superpowers/specs`、`01-面向AI` 机器文件、`02-Skills`、脚本或 `.gitignore`。
- 不访问飞书即可完成上述验收。

### 8.3 飞书侧验收边界

本次整改完成只能声明“本地发布范围已收紧并通过回归”。在完成单独的远端清理并读回核验前，不声明飞书现有测试树已整改完成。

## 9. 变更记录的归属

- 正文修改、权限变化、审批和页面版本历史：由飞书保存。
- Schema、字典、准入规则、发布清单和代码修改：由 Git 提交与评审历史保存。
- 同步任务、权限失效、索引清理和失败重试：由独立运行审计记录保存，不写进公司知识正文；治理验证阶段只保留必要的脱敏证据。
- 任何审计记录只能证明一次操作，不替代对应飞书正文或 Git 机器规则的权威地位。

## 10. 安全与回退

- 发布清单本身保存在 Git，由代码审查和提交历史追踪变更。
- 不从命令行或仓库读取飞书密钥，沿用 macOS 钥匙串方案。
- 不新增节点删除或移动权限。
- 若新扫描逻辑异常，可通过 Git 回退代码和清单；现有飞书测试树不受本次本地整改影响。
- Git 回退机器规则不得自动回退飞书正文；正文回退必须使用飞书版本能力并由文档负责人确认。
