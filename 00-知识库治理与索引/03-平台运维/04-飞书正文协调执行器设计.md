# 飞书正文协调执行器设计

> 状态：已批准（2026-08-25）。本文是 Git 控制面的技术设计，不属于公司知识库正文，不发布到飞书。

## 1. 目标与已确认范围

执行器用于受控执行 `.runtime/feishu-body-reconciliation-plan.json`。当前已确认的计划摘要为：

`399f88bfcea18b69b55a1eb6a2eb325c35782a8956664a02ae244e282410724f`

计划包含 17 个页面动作和 1 个目录原位改名动作：3 页合并到存续页、4 页更新正文、5 页改名并更新正文、5 个旧页改为兼容跳转，以及 `模板` 原位改名为 `11-模板`。

执行器不得创建、删除或移动知识库节点，不得修改成员、权限或 ACL，不得读取或修改 `Validation&Verification`，不得改变 `production_index_enabled=false`。

## 2. 权威边界

- 飞书：执行前和执行后的页面正文、标题、父子关系、精确 revision 与版本历史。
- Git：发布清单、路径迁移、协调计划 Schema、执行器代码和稳定治理规则。
- `.runtime`：协调计划、执行日志和发布状态；均可重建、Git 忽略、权限为 `0600`。
- 用户确认：必须与计划内完整 `plan_digest` 精确相等；不能使用简称、旧摘要或仅确认数量。

## 3. 命令契约

新增独立入口 `scripts/feishu-governance-coordinate-apply.mjs`，不复用普通发布器的宽泛 `apply`：

```bash
node '00-知识库治理与索引/03-平台运维/scripts/feishu-governance-coordinate-apply.mjs' \
  apply \
  --plan '00-知识库治理与索引/.runtime/feishu-body-reconciliation-plan.json' \
  --confirm-plan-digest '<完整 SHA-256>' \
  --execute
```

缺少任一参数、摘要不一致、计划 Schema 不受支持、运行模式不是 `governance_validation`，或计划包含未实现动作时，必须在认证和写请求前失败。

## 4. 组件边界

### 4.1 计划加载器

- 校验 `schema_version=1.1`、`plan_digest`、17 个页面动作和 1 个目录动作。
- 校验动作 ID、幂等键、路径唯一性、精确 revision 和不可逆节点引用。
- 重新生成当前 Git 提案块，并核对每个 `proposal` 摘要。

### 4.2 只读新鲜度检查器

- 使用 tenant 应用身份重新读取全部 17 页和 1 个目录。
- 页面必须同时匹配 revision、原始正文哈希、标题、父节点、受控标记和身份范围。
- 目录必须同时匹配标题、父节点和身份范围，且目标标题无冲突。
- 调用既有 `assertWholePlanFresh`；任一对象漂移使整份计划失败，写请求数必须为零。

### 4.3 精确版本写客户端

- 只暴露三类写方法：追加文档块、删除已验证的旧块范围、更新节点标题。
- 文档块写请求必须使用上一只读步骤冻结或上一写响应返回的精确 revision，禁止 `document_revision_id=-1`。
- 每个写阶段在请求前把 `client_token` 写入执行日志；限流重试复用同一 token。
- 写响应缺少新 revision 时，立即只读获取元数据；若 revision 未前进或正文状态不符合预期则停止。

### 4.4 执行日志

文件：`.runtime/feishu-body-reconciliation-execution.json`。

记录计划摘要、原发布状态摘要、阶段、每个动作的状态、已持久化 client token、写前/写后 revision、读回摘要、错误分类和时间。执行日志不保存访问令牌、App Secret、原始节点 token 或完整正文。

## 5. 页面状态机

每个页面动作独立执行，顺序固定且串行：

1. `pending`：重新读取精确 revision、标题和正文。
2. `baseline_verified`：必须与计划的 `expected_remote` 完全一致。
3. `new_body_appending`：按不超过 50 块分批追加新正文；每批使用精确 revision。
4. `new_body_appended`：只读验证页面恰好为“完整旧正文 + 完整新正文”。
5. `old_body_deleting`：使用当前精确 revision 删除已验证的旧块范围。
6. `body_verified`：只读验证页面只剩完整新正文，且提案签名一致。
7. `title_updating`：仅在源标题与目标标题不同时原位改名；旧页兼容跳转不改标题。
8. `complete`：只读验证标题、正文、父节点和节点身份。

先追加再删除，避免进程中断时出现空页面。若在追加后中断，页面可能暂时同时包含旧正文和新正文；恢复流程必须识别并完成删除，不再次追加。

## 6. 恢复与幂等规则

恢复时逐页只读识别三种允许状态：

- 完整旧正文：从追加阶段继续。
- 完整旧正文加完整新正文：从删除旧块阶段继续。
- 完整新正文：跳过正文写入，继续标题和最终核验。

其他状态一律视为未知并发修改，停止整批执行。已完成动作必须再次读回验证，不能仅信任本地执行日志。

同一计划摘要允许恢复；计划摘要、应用身份、空间、受管根节点或原发布状态摘要变化时禁止复用旧执行日志。

## 7. 执行顺序

1. 更新 12 个存续页面，确保新入口正文先就绪。
2. 将 5 个旧页面改为兼容跳转。
3. 原位改名 `模板` 目录为 `11-模板`，并按精确 revision 同步该目录页的受控路径标记。
4. 原子更新本地发布状态，把活跃页面路径迁移到新路径，并保留 5 个旧页记录。
5. 执行完整只读核验。

任何动作失败时立即停止，不继续后续动作。执行器不自动回滚已完成动作；飞书版本历史作为人工恢复依据，执行日志用于受控续跑。

## 8. 本地发布状态更新

全部远端动作完成并读回通过后，才生成新的 `feishu-publication-state.json`：

- 12 个活跃正文记录使用新规范路径、标题、父路径、正文摘要和块数。
- 5 个旧页记录保留原路径，并记录兼容跳转正文摘要。
- `模板` 目录记录迁移为 `11-模板`，其 3 个子页面父路径同步更新。
- 保留空间、受管根、退役历史和迁移审计字段。
- 使用临时文件加原子重命名写入，文件权限保持 `0600`。

若远端已全部完成但本地状态原子更新失败，执行日志标记 `remote_complete_state_pending`；恢复时先完整读回，再仅完成本地状态更新，不重复发送远端写请求。

## 9. 最终核验与成功标准

- 17/17 页面节点身份和父子关系正确。
- 12/12 活跃正文与当前 Git 提案签名一致。
- 5/5 旧页面为受控兼容跳转，链接到对应存续页面。
- 1/1 目录原位改名成功、受控路径标记已同步且不存在同名冲突。
- 132 个目录、12 个活跃正文和 5 个兼容页均可由本地状态定位。
- 创建、删除、移动、ACL 和生产索引变更请求均为零。
- 执行日志状态为 `complete`，并记录写请求数量与最终计划摘要。

## 10. 回归测试

本机回环模拟至少覆盖：

1. 摘要或数量不一致时零写入。
2. 页面 revision、正文、标题、父节点或身份范围漂移时零写入。
3. 目录标题冲突时零写入。
4. 多批追加全部使用精确递增 revision。
5. 追加后中断并恢复，不重复追加。
6. 删除后中断并恢复，不重复删除。
7. 已完成动作重复执行保持幂等。
8. 任一页面失败后不执行后续页面。
9. 全部成功后状态文件原子迁移。
10. 日志和错误输出不包含凭证、原始节点 token 或正文。

真实执行前必须通过既有治理全量回归、发布/退役回环回归和新增执行器回归。

## 11. 风险与处置

- 飞书不提供跨 17 页原子事务：通过串行执行、逐页读回、立即停止和执行日志降低风险。
- 追加与删除之间中断会短暂出现重复正文：恢复状态机负责识别并完成协调；优先保证页面不为空。
- 用户在执行期间编辑页面会导致 revision 冲突：停止，不覆盖，重新生成计划并确认。
- 写接口响应或限流行为与模拟不一致：停止并保留日志，不猜测远端状态。
- 自动回滚可能覆盖执行后的人工编辑，因此不实现自动回滚；需要时依据飞书版本历史人工恢复。
